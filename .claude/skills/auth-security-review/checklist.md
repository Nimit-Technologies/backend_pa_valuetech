# Auth security checklist

Reference for [SKILL.md](SKILL.md). Each section lists what to verify in the actual code, plus the CWE/OWASP reference to cite when it fails.

## A. Password security

**Storage** — CWE-916 (Insufficient Computational Effort), OWASP A02:2021 (Cryptographic Failures)
- Hashed with bcrypt/Argon2/scrypt, never MD5/SHA1/plain reversible encryption
- Salt is unique per password and generated by the hashing library (not hand-rolled)
- Work factor: bcrypt cost ≥ 12, or the Argon2/scrypt equivalent
- Comparison uses the library's constant-time compare, not `===` on hashes

**Policy** — CWE-521 (Weak Password Requirements)
- Minimum length ≥ 12, no arbitrary maximum that truncates entropy
- Password change requires the current password
- No plaintext password ever logged, stored, or included in an error/response

**Account protection** — CWE-307 (Improper Restriction of Excessive Authentication Attempts)
- Lockout or exponential backoff after repeated failed attempts on one account
- Rate limiting on the login route by IP, independent of per-account lockout
- Failed attempts don't reveal whether the account exists (see Section F)

## B. Session & cookie management

**Session ID** — CWE-330 (Use of Insufficiently Random Values)
- Generated with a CSPRNG (`crypto.randomBytes`, framework default), not `Math.random()` or a predictable counter
- ID itself carries no meaning (not a user ID, timestamp, or derivable value)

**Lifecycle** — CWE-384 (Session Fixation), CWE-613 (Insufficient Session Expiration)
- New session/token issued on login — the pre-login session ID is never reused post-auth
- Session/refresh token invalidated server-side on logout, not just cleared client-side
- Idle and absolute timeouts both exist and are enforced server-side
- Password change invalidates other active sessions for that user

**Cookie flags** — CWE-614 (Sensitive Cookie Without 'Secure' Flag), CWE-1004 (Sensitive Cookie Without 'HttpOnly')
```js
res.cookie('token', value, {
  httpOnly: true,      // required — blocks JS/XSS access
  secure: true,         // required in production — HTTPS only
  sameSite: 'strict',   // or 'lax' if cross-site flows need it — justify if not 'strict'
  path: '/',             // no broader than needed
  maxAge: <bounded>,     // no session cookie that never expires
});
```
- Check the actual `cookie-option`/config file, not just call sites — a shared default that's wrong affects every cookie set from it

**Security headers** — OWASP A05:2021 (Security Misconfiguration)
- `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options` (or CSP `frame-ancestors`), `Content-Security-Policy` set at the app or proxy level

## C. Input validation & injection

**SQL/Prisma injection** — CWE-89, OWASP A03:2021 (Injection)
```js
// FLAG THIS — raw string interpolation into a query:
await prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`);

// EXPECTED — parameterized:
await prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`;
// or the generated client's typed query builder
```
- Every `$queryRawUnsafe`/`$executeRawUnsafe` call is a finding unless the interpolated value is a fixed identifier, never user input
- Zod (or equivalent) schema validates shape, type, and length of every login/register field before it reaches the query layer

**Other injection vectors** — CWE-90 (LDAP), CWE-78 (OS Command), CWE-93 (CRLF)
- No user input reaches `exec`/`spawn`, an LDAP filter, or an email header unsanitized
- Email/username fields don't get reflected into HTML error pages unescaped (stored/reflected XSS)

## D. CSRF protection

CWE-352, OWASP A01:2021 (Broken Access Control)
- State-changing routes (login excluded, but logout/password-change included) require either: a CSRF token tied to the session, or `SameSite=Strict/Lax` cookies plus Origin/Referer validation
- If the API is pure JSON consumed by a separate frontend with `SameSite` cookies, confirm that's the actual deployment shape before waving this off

## E. Logout

CWE-613 (Insufficient Session Expiration)
- Server-side session/refresh token is destroyed, not just the cookie cleared client-side
- Cookie is cleared with matching `path`/`domain`/`sameSite` attributes — a mismatched `clearCookie` call silently fails to remove it
- A token captured before logout (e.g. via XSS or a proxy log) is rejected after logout, not just the browser's copy

## F. Error handling & information disclosure

CWE-203 (Observable Discrepancy — user enumeration), OWASP A09:2021 (Security Logging and Monitoring Failures)
- Login failure responses are identical (message, status code, timing) whether the account doesn't exist or the password is wrong
- No stack traces, ORM/DB errors, or internal paths reach the response body in production
- Registration/forgot-password flows don't confirm or deny an email's existence

## G. Logging

CWE-778 (Insufficient Logging), CWE-532 (Insertion of Sensitive Information into Log File)
- Login success/failure, logout, lockout, and password change are logged with timestamp, user identifier, and IP — never the password or full token
- Logs are structured, not string-concatenated, so they can actually be queried during an incident

## H. JWT (if used instead of, or alongside, server-side sessions)

CWE-347 (Improper Verification of Cryptographic Signature), OWASP A02:2021
- Algorithm is pinned explicitly on verify (`{ algorithms: ['HS256'] }` or similar) — never `alg: none`, and the verify call can't be tricked into accepting a different algorithm than the one used to sign
- Secret/key is loaded from environment/secret storage, not hardcoded, and has real entropy
- `exp` is set and enforced; short-lived access token + longer-lived, rotatable refresh token, not one long-lived token for everything
- Token isn't stored in `localStorage`/`sessionStorage` if it's also usable for authenticated requests (XSS would exfiltrate it) — prefer `httpOnly` cookie
- There's a way to revoke a token before its `exp` (revocation list, refresh-token rotation, or short enough expiry that this is an accepted tradeoff — state which)

## I. Rate limiting & general API hygiene

OWASP A04:2021 (Insecure Design)
- Login, register, and password-reset routes each have their own rate limit — not just a global one
- CORS config on auth routes is explicit (no reflected `Access-Control-Allow-Origin: *` with credentials)

## Manual test ideas worth naming in the report

Only include these if they're realistic to actually run, not as a generic checklist filler:
- Reuse a session/JWT after logout — confirm it's rejected
- Compare response time/body for a nonexistent account vs. a wrong password
- Send a request with the CSRF token stripped/wrong to a state-changing auth route
- Attempt `$queryRawUnsafe`-style injection on any raw-query input found in step 1
